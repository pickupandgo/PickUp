What changed from the proposals below.
  • Booking registration carries no amount. It is POST /v1/internal/bookings { externalRef, customerSubject, quoteId, paymentMethod }; confirmedFarePaise is gone and any amount field is rejected (400). The fare lives only in the server quote (POST /v1/fare/quotes), which the booking references by quoteId and the backend freezes per drop. The “where is the fare calculated” decision is settled: the server quote is authoritative.
  • Only PAY_AT_PICKUP and PAY_AT_DELIVERY for new bookings. PREPAID_UPI / pay-online-before-dispatch is retired for new bookings (refused 422) and kept only for historical rows; the prepaid-timing decision is closed.
  • PAY_AT_PICKUP is paid at the pickup before handover; PAY_AT_DELIVERY is paid per drop, before each drop's handover, for that drop's amount (UNPAID → PARTIALLY_PAID → PAID) — not once after the last drop.
  • paymentGate (stage, stopSequence, paymentState, amountPaise, handoverAllowed) is derived by the backend; the engine never sends PAYMENT_CONFIRMED, an amount, a fee or a payment status, and a handover is allowed only when handoverAllowed is true.
  • Gated OTPs, Firebase on every call, a durable outbox and a persistent engine are all in place; the identity comes from the token, and gated transitions apply only after the backend's 2xx.

1.2 Inside the payment backend

One NestJS application, shipped as one Docker image, with one PostgreSQL database. It is a modular monolith: separate modules inside, one transaction boundary. That matters for money: a cash collection and its platform-fee debit, or a trip completion and its driver earning, happen in one database transaction, so money is never half-moved.

paymentsRazorpay orders for booking payments and wallet top-ups; verification; webhooks; disputes.payments, payment_events, payment_disputes
collectionsPay-at-pickup and pay-at-delivery: cash records and booking-linked UPI QR.payment_collections

auditAppend-only record of every admin money action, with reason.admin_actions
  • Background jobs run inside the same process: the payout scheduler (Monday 11:00 IST by default) and the settlement pull (every 60 minutes by default). Both are safe with several copies running: the weekly batch has one key per ISO week, and recording a settlement twice is a no-op.
  • Scaling: stateless HTTP, so several copies can run behind a load balancer. One change first: the rate limiter counts in memory, so it needs Redis before a second copy.
  • Database roles: a migrator role owns the schema and runs migrations and the ops CLI. The API runs as a restricted role that can never DELETE or TRUNCATE, can only INSERT into the ledger, can UPDATE only listed columns, and can only read identity tables (users, drivers, customers). Triggers and CHECK constraints enforce the money rules a second time, inside the database.

2. Rules that keep the money safe

Every change in the engine or the admin panel has to respect these. They are enforced in the payment backend's code and, where possible, by the database itself.

  1. Integer paise everywhere. 100 paise = ₹1. No floating point on money, in any service.
  2. The fare is frozen at confirmation. The engine registers it once; it never changes. Every later amount (Razorpay order, QR, cash figure, fee, earning) comes from it.
  3. No app ever sends an amount the server uses. The booking payment has no amount field; a collection's amount must equal the fare and is only a confirmation.
  4. The fee rule is pinned at confirmation. Changing commission later never changes an existing booking.
  5. Only the server decides a payment happened, after checking with Razorpay (verify call, webhook or admin sync). An app's "success" callback is never proof.
  6. A trip can't complete while unpaid. COMPLETED is refused with 409 PAYMENT_REQUIRED.
  7. One live payment per booking. Every retry returns the same Razorpay order.
  8. Everything that creates something is idempotent. Retries never charge, credit or pay twice.
  9. The wallet ledger is append-only and the wallet never goes negative. The wallet only funds cash-trip fees; it is not earnings and can't be withdrawn.
  10. An online earning is payable only after Razorpay settles the money to Nikhil Enterprises, not at payment or completion.
  11. Payouts go only to bank accounts an admin approved after a bank validation, and a driver's account change needs a phone OTP step-up.
  12. Every admin money action needs a written reason and is recorded in the audit trail.

4.1 Booking confirmation and registration

The engine learns the booking is paid by reading GET /v1/internal/bookings/{id} (paymentStatus: PAID, paidWith: PREPAID_ONLINE). Whether dispatch waits for payment is decision 9.

4.3 Pay at pickup or delivery: cash or UPI QR

The engine only registers the method (PAY_AT_PICKUP or PAY_AT_DELIVERY) and reports trip statuses. Collection is between the Driver App and the payment backend:

  1. The collection window opens from the engine's status reports: PAY_AT_PICKUP from DRIVER_ARRIVED until DELIVERED; PAY_AT_DELIVERY only at DELIVERED. The Driver App sees collectionOpen: true on GET /v1/trips/{tripId}.
  2. Cash: POST /v1/trips/{tripId}/collections {method: CASH, amountPaise: fare}. In one transaction the backend records the cash, takes the platform fee from the driver's wallet (CASH_RIDE_FEE) and marks the booking paid. If the wallet can't cover the fee: 409 INSUFFICIENT_BALANCE, nothing is recorded; the driver recharges and retries with the same key.
  3. UPI QR: same call with ONLINE_QR. The backend creates a booking-linked Razorpay UPI QR; the customer pays from any UPI app; the backend learns it from the qr_code.credited webhook or when the Driver App polls the collection. Asking twice returns the same open QR.
  4. Recording cash while a QR is open closes the QR first; if the QR was already paid, the cash is refused (409 BOOKING_ALREADY_PAID).
  5. The engine then sends COMPLETED; it succeeds once the booking is paid.

4.4 Trip completion and the driver's earning

  • The engine reports each step in order. For cash and QR bookings, expect 409 PAYMENT_REQUIRED on COMPLETED while the driver is still collecting: retry on a schedule. This retry is required, not an error path.
  • On success: booking and trip COMPLETED, and exactly one driver earning: gross = fare, platform fee from the pinned rule, net = gross − fee − other deductions (0) − TDS (0 while TDS is disabled).
  • Example: fare ₹500 → fee ₹50 (10%) → net ₹450.

4.5 Cancellation

  • The engine calls POST /v1/internal/bookings/{id}/cancel {reason} for every cancellation: customer, driver, admin, or dispatch finding nobody.
  • The booking and its trip become CANCELLED; any open payment QR is closed at Razorpay.
  • A paid booking can still be cancelled. It is listed in the paid-cancelled-bookings report for refund review. Nothing is refunded automatically and there is no refund API yet.
  • Money arriving after cancellation is recorded and flagged; an authorized payment for a cancelled booking is never captured.

4.6 Driver wallet recharge

Driver App → POST /v1/wallet/topups {amountPaise} (Idempotency-Key) → Razorpay Checkout → POST /v1/wallet/topups/{paymentId}/verify → wallet credited (TOPUP). The wallet exists only so the platform fee on cash trips can be taken. It is not earnings, and it can't be withdrawn.

4.7 Earning to the driver's bank account

trip COMPLETED (online) ---> earning AWAITING_SETTLEMENT Razorpay settles the payment to Nikhil Enterprises (hourly pull, settlement.processed webhook, or admin sync) ---> earning PAYABLE Monday 11:00 IST: scheduler pulls settlements, prepares batch "schedule:" = every PAYABLE, settled earning whose driver has a VERIFIED bank account one payout per driver; earnings IN_PAYOUT; batch PREPARED Admin reviews the batch and executes it (unless PAYOUT_AUTO_EXECUTE=true) ---> RazorpayX payout per driver (idempotent reference) ---> SUBMITTED RazorpayX webhook payout.processed ---> payout PROCESSED + UTR, earnings PAID payout.failed ---> payout FAILED, earnings back to PAYABLE (next batch) payout.reversed ---> payout REVERSED, earnings ON_HOLD, bank account SUSPENDED Missed webhook: POST /v1/admin/payouts/{id}/sync

4.8 Driver bank account: OTP step-up, bank validation, admin approval

  1. Driver App → POST /v1/bank-account/change-requests → {changeRequestId, expiresAt (10 min), stepUp: {method: FIREBASE_PHONE_REAUTH, phoneNumberHint, notBefore}}.
  2. The driver re-authenticates with a Firebase phone OTP on the registered number. The fresh ID token's auth_time is after the request; a stolen session can't produce that.
  3. Driver App → POST .../{id}/confirm {accountHolderName, ifsc, accountNumber, confirmAccountNumber} with that token. The previous verified account is suspended in the same transaction; the new one is PENDING_VERIFICATION and a bank validation (penny drop) starts. Only the last 4 digits are stored.
  4. RazorpayX reports the result (webhook): account active or invalid, the bank's registered name, and our name match against the KYC legal name: MATCH, PARTIAL, MISMATCH or UNAVAILABLE.
  5. Admin reviews and approves (VERIFIED), rejects, or suspends. Anything other than an exact MATCH needs a written mismatchResolution, which is audited.

4.9 Disputes

Razorpay payment.dispute.* webhooks are recorded against the booking. The trip's earning is put on hold if it is still AWAITING_SETTLEMENT or PAYABLE; if it is already in a payout or paid, it is flagged for ops. Disputes show in the webhook-anomalies report.

4.10 Daily operations

The reconciliation reports in section 7.9 should normally be empty. Each non-empty one is a task for a person: refund review, a missed webhook to sync, a stuck payout, a driver owed money without a verified bank account.

5. The fare

5.1 How it works today

Checked in the current code of the Customer App and engine-v2:

  1. The Customer App's fare screen calls the engine's GET /fare/estimate with the pickup, the first drop only and the weight. It does not send the vehicle type or the other drops.
  2. The app sends that number as fare in POST /rides.
  3. The engine calculates the correct multi-drop fare, then ignores it: const fare = dto.fare || fareEstimate.fare. The app's number wins.
EffectWhy it matters with real money
The client sets the priceA modified app can book any job for ₹1.
Extra drops aren't chargedA 5-drop job is priced as pickup to the first drop; the extra legs and the ₹10 per extra stop are lost.
Vehicle type isn't appliedThe multiplier (0.8 two-wheeler to 2.0 pickup truck) is never used, so trucks are priced like three-wheelers.
Straight-line distanceHaversine distance is shorter than the road distance, so long or winding routes are underpriced.
Pricing is hard-codedBase ₹30, ₹12/km, ₹10 per extra stop, vehicle and weight multipliers are constants in FareService. The admin panel's pricing pages can't change anything.

5.2 What the payment backend needs

Whatever you decide about where the fare is calculated, the payment backend's contract doesn't change: it receives one integer, confirmedFarePaise, at registration, and freezes it. It never recalculates, adjusts or adds to it. Surcharges, extra stops and anything else the customer pays must already be inside that number.

5.3 Proposed: a server-side quote decision 1

Recommended: the engine stays the fare authority, because it already has the route, stops, vehicle and weight. The change is to make its number the only number:

Customer App Trip Engine Payment Backend POST /v1/fare/quotes calculate with the current pricing version { pickup, drops[1..5], store the quote: customer, inputs, result, vehicleCategory, weightKg } pricingVersion, expiresAt (e.g. 10 min) <------------------------------- { quoteId, farePaise, breakdown, distanceKm, durationMin, expiresAt } POST /v1/bookings load the quote: same customer, not expired, { quoteId, paymentMethod, not used, same inputs; mark it used contacts, goods } booking.farePaise = quote.farePaise (no amount) POST /v1/internal/bookings ----------------> fare frozen <------------------------------- { bookingRef, paymentBookingId, farePaise }
  • Expired quote: 409 (e.g. QUOTE_EXPIRED). The app re-quotes and shows the new price before the customer confirms. The customer always pays exactly the price they saw.
  • Pricing rules move into the engine's database, edited from the admin panel's Fare & Pricing and Surcharges pages. Make them versioned, never edited in place: a change is a new version with an effective time, and each quote records the version it used, so any fare can be explained later. This is the same model the payment backend uses for fee rules.
  • Distance on the server. Never take a distance from the app. Road distance (for example Google's Distance Matrix, called from the engine with a server key) is fairer than straight-line; that is decision 2.
  • Compute in paise, round once per the pricing rules, and send the integer.

The alternative is calculating the fare inside the payment backend. Not recommended: it would need locations, stops, goods and road distance, which the payment backend deliberately doesn't hold; pricing changes would mean deploying the money service; and it changes a tested system. The contract with the engine would stay the same either way.

5.4 Pricing is not commission

ConceptLives inWhat it decides
Pricingengine (proposed)What the customer pays: base fare, per km, extra stops, weight, vehicle, minimum fare, surcharges.
Commissionpayment backend fee_rulesHow the fare is split: platform fee, and the driver's share. Changing it never changes the customer's price.
Three pricing items in the admin panel need a decision before they're built
  • Surcharges (traffic, rain): allowed only if applied inside the quote. V1 has no price changes after confirmation.
  • Insurance premium: if it goes inside the fare, the platform fee and the driver's share would be taken from the premium too. It needs its own design (decision 8).
  • Cancellation charges: V1 has none, and there are no refunds yet. Part of the refund policy (decision 7).

7. Admin API

7.1 Conventions for the admin panel

ItemRule
AuthAuthorization: Bearer <Firebase ID token> of a user with role ADMIN. Get the token from the Firebase web SDK on every request (getIdToken()); don't store it yourself. On 401 AUTH_INVALID_TOKEN, retry once with a forced refresh. 403 FORBIDDEN means signed in but not an admin.
Browser access (CORS)The panel's origin must be listed in the backend's CORS_ORIGINS. Allowed methods: GET and POST only. Allowed headers: Authorization, Content-Type, Idempotency-Key, X-Request-Id. No cookies.
Idempotency-KeyRequired on POST /v1/admin/wallets/{id}/adjustments and POST /v1/admin/payout-batches. Format /^[A-Za-z0-9_-]{16,64}$/; a UUID is fine. Generate one per user action; reuse it on retry.
ReasonsEvery money action takes a reason of 10 to 500 characters (ticket, approval reference). It's stored and audited, so make the field required in the UI.
PaginationCursor-based where offered: ?limit=1..100&cursor=<nextCursor> → { items, nextCursor }. No page numbers or totals. Other lists return a plain array (bank accounts, batches, fee rules, settlements, reports).
Money and timeAmounts are integer paise. Timestamps are ISO-8601 UTC. Show rupees and IST in the UI.
Rate limits120 requests per minute per admin by default; money actions are lower (shown per endpoint). Over the limit: 429 RATE_LIMITED.

12. Setup and handover

12.1 Local development

  • Payment backend: PostgreSQL from docker compose on 127.0.0.1:5433; npm run db:migrate; npm run build; npm start on port 3000.
  • API docs: with SWAGGER_ENABLED=true, Swagger UI is at http://localhost:3000/docs and the OpenAPI JSON at /docs/openapi.json. You can generate a typed client from it.
  • Admin panel: run Next on another port (next dev -p 3001) and set CORS_ORIGINS=http://localhost:3001 in the backend's .env.
  • Engine: needs the backend URL and an INTERNAL_API_KEYS value, issued by Raj per environment and shared over a secure channel.

<E.164> is a phone like +919876543210; <uid> is the person's Firebase UID.

Phone numbers are unique: test the customer, driver and admin with three different numbers. Firebase test phone numbers avoid real SMS.

12.3 Razorpay test mode limits

  • UPI QR codes can't be paid in test mode; payment links can, so test mode uses a payment-link QR. Live mode refuses the payment-link QR and needs QR Codes enabled on the account.
  • Test payments never settle, so online earnings stay AWAITING_SETTLEMENT unless the development simulator is used.
  • Bank account validation isn't available in test mode; RazorpayX test payouts stay processing until moved by hand or by the simulator.

12.4 Production

  • HTTPS only; CORS_ORIGINS lists only the admin panel's domain; Swagger off.
  • Secrets (Razorpay keys, webhook secrets, internal key) in a secret store; the internal key only on the engine's server.
  • The backend logs the production-readiness items still open at startup: Razorpay live activation, QR Codes, RazorpayX, settlement verification, TDS.
